# AI 跑团个人项目：技术方案与作品化建议

> **2026-10-21 方向调整（以 PRD v0.2 为准）：**  
> - **Android 优先**（竖屏），不做桌面端；  
> - **不做 Mock 模式**，改为「团本历史归档」，仓库内置真实示例归档；  
> - **GM/BP 必须会吐槽、拒绝、善变**；  
> - 界面为 **首页 / 制卡 / 跑团** 三屏，跑团页是「桌子 + 底部对话框 + 右侧插话按钮」。  
> 本文中仍保留桌面端、Mock、旧 UI 的段落，仅作技术参考；冲突处以 [PRD/README.md](PRD/README.md) 和 [PRD/05_体验与界面.md](PRD/05_体验与界面.md) 为准。

**项目定位：个人娱乐 + GitHub 作品 + 自己长期玩**  
**核心玩法：1 个真人玩家 + 2–5 个 AI 玩家（BP）+ AI GM/KP + 真实随机骰子，在固定或自定义世界观下跑团；剧情由 AI 之间互相沟通推进。**  
**参考示例：科比特先生晚宴（仅内部参考，公开版本改为原创《顾先生的晚宴》）。**

---

## 0. 结论

**这是一个很好的个人项目，但要把「作品」和「游戏」两个目标分开设计。**

- **作为作品**：它比“又一个 AI 小说生成器”有辨识度。它能展示多智能体编排、状态管理、结构化输出、确定性模拟、Flutter UI、测试与评估——这些都是读者能看懂的技术点。
- **作为游戏**：它的乐趣不在“AI 文笔”，而在**AI 角色之间的化学反应**：B 说服失败、A 补位成功、C 在旁边拆台、NPC 记仇。你要设计的是“让 AI 互相演得好看”的机制，不是“让 AI 写得好”。
- **最大的技术难点**：不是 LLM，而是**导演（Director）+ 信息边界 + 骰子权威**。这三件事决定它是“一群聊天机器人”还是“一个跑团”。

**建议首版范围：**

> **1 个原创社交场景 + 1 个真人 + 2 个 AI 玩家 + 1 个 AI GM + 1 个 NPC + d100 检定 + 文本 + 15–20 分钟。**

不要一上来做 3–6 人 + 自定义世界 + 语音 + 地图。先把“一个场景跑得好看”做出来。

---

## 1. 这个玩法为什么值得做

### 1.1 它和市面上的产品不完全一样

| 产品 | 核心 | 你的差异 |
|---|---|---|
| AI Dungeon | 1 个玩家 + AI 叙事 | 你有 AI 队友，AI 之间会互相说话 |
| Hidden Door | 朋友组队 + AI GM | 你是“1 真人 + AI 队友”，不是真人组队 |
| Friends & Fables | 多人 + AI GM | 它的多人是真人；你的多人是 AI |
| RoleForge | 规则引擎 + 单人 | 你更强调“AI 玩家之间的社交/冲突” |
| 星野/猫箱/戏格 | 1 对 1 角色聊天 | 你有队伍、有目标、有骰子、有失败 |

**你的独特卖点：**

> **“你不是一个人在跑团，你是一个真人混在一群 AI 玩家里。”**

这更像“AI 跑团观察室 + 共演”：你可以看 AI 队友怎么勾心斗角，也可以插话改变局面。

### 1.2 它天然适合 GitHub 展示

- 有**可读归档**：读者可以 clone 下来，直接看一局真实跑团记录；
- 有**架构图**：Flutter + 后端 + 多 Agent + 规则引擎 + 骰子服务；
- 有**可视化日志**：每回合谁说了什么、骰子多少、谁知道了什么；
- 有**可讨论的工程取舍**：为什么规则引擎不交给 LLM、为什么骰子要服务端、为什么需要导演；
- 有**评估集**：同一场景跑 20 次，看角色一致性、剧情张力、信息泄露。

这些比“我做了个 AI 小说 App”更能体现工程能力。

## 2. 核心难点：不是写故事，是“编排”

### 2.1 多智能体对话的三个问题

1. **谁先说？**  
   如果让 LLM 自由发言，它要么抢话，要么冷场，要么无限互相客气。
2. **谁该知道什么？**  
   B 不知道 C 的 secret；NPC 不知道玩家的内心；GM 知道全部。信息边界错了，剧情就崩。
3. **谁来决定成败？**  
   如果让 LLM 决定骰子结果，它会讨好玩家；必须由规则引擎/骰子服务裁决。

### 2.2 解决方案：一个“导演”层

不要让 Agent 自由对话。加一个**Director（导演）**，它不一定用 LLM，可以是确定性状态机：

```
Director 决定下一个行动者
  ├─ 场景目标需要推进？→ 选最相关的人
  ├─ 有人太久没说话？→ 给他 spotlight
  ├─ 真人玩家太久没行动？→ 提示真人
  ├─ AI 之间聊太久？→ 插入事件/切场景
  └─ 场景目标达成/时钟满？→ 结算/转场
```

**Director 的职责：**

- 控制节奏（beat / scene / act）；
- 分配 spotlight；
- 防止 AI 互相客套/无限循环；
- 在合适的时候让 GM 要骰子；
- 在合适的时候把话语权交给真人；
- 记录“谁知道了什么”。

**关键原则：**

> **Agent 负责“演”，Director 负责“剪”，Rules Engine 负责“判”，Dice 负责“随机”。**

## 3. 游戏设计：让 AI 之间“有戏”

### 3.1 每个 AI 玩家都要有“戏点”

不要给 AI 玩家只写“性格：友善”。要写：

- **目标**：这次场景我想要什么（B 想拉科比特入伙）；
- **秘密**：我不想让人知道的事（B 其实欠了债）；
- **关系**：我对 A/C 的态度（B 不信任 C）；
- **恐惧/底线**：什么会让我退缩；
- **说话风格**：3 个关键词 + 1 句示例。

这样 AI 才会“有立场”，而不是永远附和。

### 3.2 场景要有“时钟”和“代价”

以科比特晚宴为例：

- **场景目标**：让科比特接受邀请；
- **NPC 耐心时钟**：3 格；每次失败社交检定 -1；到 0 他关门；
- **线索**：科比特提到“刚结束一次会面”——这可能是线索；
- **代价**：失败不是“重来”，而是“他更警惕/时间更晚/邻居起疑”。

**失败前进（fail forward）**：

- 失败不是“什么都不发生”，而是“发生更糟的事”；
- 大失败可以暴露玩家的意图，让 NPC 起疑；
- 成功也不一定全赢，可能附带条件（“可以，但我带个朋友”）。

### 3.3 回合结构：不是严格轮流，是“ spotlight ”

推荐**场景制 + spotlight**，不是 D&D 式严格 initiative：

```
Scene 开始
  → GM 描述场景 + 给出目标
  → Director 选第一个行动者（通常是 NPC 或最相关的人）
  → 行动者说话/行动
  → 如果需要检定：GM 要骰 → 骰子服务 → GM 叙述结果
  → 更新状态（耐心/线索/关系）
  → Director 选下一个
  → 场景目标达成 / 时钟满 / 玩家离开 → 场景结束
```

**谁获得 spotlight：**

- 有相关技能/知识的人；
- 还没说过话的人；
- 和当前冲突最相关的人；
- 真人玩家（每 2–3 个 beat 至少给一次机会）。

**防冷场：**

- 连续 2 次 AI 对 AI 对话后，Director 强制把话筒给真人，或插入事件（门铃、电话、邻居路过）；
- 连续 3 次没有新信息，Director 让 GM 推进时钟/给线索。

### 3.4 骰子：真实随机 + 服务端权威

**规则示例（d100 roll-under）：**

- 技能值 50，骰出 41 → 成功；
- 骰出 81 → 失败；
- 骰出 01–05 → 大成功；
- 骰出 96–100 → 大失败；
- 困难检定：技能值减半；极难：1/5。

**实现：**

- 服务端 `secrets.randbelow(100) + 1`；
- 记录 `session_id, actor, skill, skill_value, difficulty, die, outcome, timestamp`；
- 可选：用 HMAC(server_secret, roll_data) 生成校验码，证明骰子没被改；
- **GM 先声明检定和难度，骰子后出结果，GM 再叙述**——防止 LLM 事后编结果；
- UI 显示：`【话术】 41 / 50 → 成功`，让玩家信任。

### 3.5 信息边界：谁该知道什么

| 角色 | 知道 | 不知道 |
|---|---|---|
| **GM** | 全部剧本、NPC 秘密、线索、时钟 | — |
| **NPC** | 自己的目标/秘密、公开对话、自己观察到的事 | 玩家的内心、其他 NPC 的秘密 |
| **AI 玩家 B** | 自己的角色卡/秘密/关系、公开对话、自己发现的线索 | C 的秘密、NPC 的隐藏动机 |
| **真人 A** | 自己的角色卡、公开对话、自己发现的线索 | 同上 |

**实现：**

- 每个 Actor 一个 `KnowledgeBase`；
- 事件带 `visible_to`；
- 构建 prompt 时只注入该 Actor 可见的事件；
- GM 的 prompt 单独注入完整剧本；
- 不要让“快线叙事者”知道秘密（参考 Hidden Door 的 differential knowledge）。

### 3.6 AI 对话的质量控制

**问题：** AI 容易互相客气、重复、附和、抢话、替别人说话。

**对策：**

- 输出 schema 强制：`{dialogue, action, intent, target, private_thought}`；
- 禁止“替别人说话/替别人做决定”；
- 每个 AI 玩家有“本场目标”，每回合提醒；
- 给 AI 玩家“不同意”的许可：`You may disagree, withhold information, or pursue your own goal.`；
- 给 GM“切场景/要骰/给后果”的工具；
- 用便宜模型做 AI 玩家，强模型做 GM；
- 每回合限制 1–3 句话，避免长篇大论。

## 4. 技术架构

### 4.1 总体

```
Flutter App
  ├─ 对话流 / 角色卡 / 骰子卡 / 线索板 / 日志
  └─ WebSocket / SSE
        │
FastAPI 后端
  ├─ Session Service（会话/存档）
  ├─ Director（回合/spotlight/转场）
  ├─ Agent Runtime（GM / NPC / AI PC）
  ├─ Rules Engine（d100 检定/资源/状态）
  ├─ Dice Service（服务端随机）
  ├─ Memory / Knowledge（事件日志 + 摘要）
  ├─ Moderation（内容安全）
  └─ SQLite（单机个人项目足够）
```

### 4.2 为什么选这些

| 层 | 选择 | 理由 |
|---|---|---|
| 客户端 | Flutter | 跨平台、UI 快、适合作品 |
| 后端 | Python + FastAPI | LLM 生态好、async 编排方便、代码可读 |
| 数据库 | SQLite | 单用户、零部署、方便 clone 即跑 |
| 实时 | WebSocket/SSE | 流式叙述、打字机效果 |
| LLM | OpenAI-compatible | 支持 DeepSeek/Qwen/OpenAI/Claude，BYOK |
| 规则 | 自研 d100 | 简单、可控、避免 CoC/D&D 版权 |
| 部署 | 本地 + Docker（可选） | 个人玩；作品可一键跑 |

> 不建议为了“看起来高级”上 Postgres/Redis/K8s。个人项目**clone 即跑**比“架构复杂”重要。

## 5. Agent 设计

### 5.1 GM / KP

**职责：**

- 描述场景、推进剧情；
- 扮演 NPC；
- 判定行动是否需要检定；
- 要骰、叙述结果；
- 管理时钟/线索/场景目标；
- 在合适的时候结束场景。

**输入：**

- 完整剧本（场景目标、NPC 秘密、线索、时钟）；
- 公开对话；
- 当前状态；
- 规则（d100、技能列表、难度）。

**输出 schema：**

```json
{
  "narration": "科比特先生扶着门框，目光在你们两人之间来回。",
  "npc_dialogue": [
    {"npc": "Corbitt", "line": "按照礼节，我不该回绝……但我刚结束一次会面，实在疲惫。"}
  ],
  "check": {
    "actor": "B_Stella",
    "skill": "话术",
    "difficulty": "regular",
    "target": 50,
    "reason": "邀请科比特参加餐会"
  },
  "state_updates": [
    {"type": "clock", "name": "corbitt_patience", "delta": -1}
  ],
  "scene_status": "continue"
}
```

**约束：**

- 不能替玩家决定行动；
- 不能编造骰子结果；
- 不能泄露 NPC 不知道的秘密；
- 每次只推进一个 beat。

### 5.2 AI 玩家（PC）

**职责：**

- 以自己的角色身份说话/行动；
- 追求自己的目标；
- 可以同意、反对、隐瞒、试探；
- 在需要时请求检定（由 GM 决定是否要骰）。

**输入：**

- 角色卡（属性/技能/性格/目标/秘密/关系）；
- 公开对话；
- 自己可见的线索；
- 本场目标；
- 当前 spotlight 原因。

**输出 schema：**

```json
{
  "dialogue": "您好，科比特先生，我是 Stella。这是我的朋友 Joe……",
  "action": "邀请科比特先生参加餐会",
  "intent": "persuade",
  "target": "Corbitt",
  "private_thought": "我需要他的商业渠道，不能让他拒绝。",
  "request_check": true
}
```

**约束：**

- 只代表自己；
- 不决定成败；
- 不替其他角色说话；
- 1–3 句话；
- 可以有自己的小算盘。

### 5.3 NPC

**职责：**

- 按自己的目标/秘密/性格回应；
- 可以被说服、激怒、欺骗；
- 记住玩家之前的行为。

**输入：**

- NPC 卡（目标/秘密/态度/耐心）；
- 公开对话；
- 自己观察到的事。

**输出：**

- 对话 + 表情/动作 + 态度变化。

### 5.4 Director

**职责：**

- 选下一个行动者；
- 控制 beat 数；
- 防循环；
- 触发转场/事件；
- 给真人玩家留 spotlight。

**输入：**

- 场景目标；
- 每个 Actor 的最近行动时间；
- 当前时钟/线索；
- 对话轮数；
- 是否有人被冷落。

**输出：**

```json
{
  "next_actor": "A_Human",
  "reason": "human_has_been_silent_3_beats",
  "inject_event": null
}
```

**规则示例：**

| 条件 | 动作 |
|---|---|
| 真人 3 beat 没说话 | 把 spotlight 给真人 |
| AI 对 AI 连续 2 轮 | 插入事件/让 GM 推进时钟 |
| 场景目标达成 | 转场/结算 |
| 时钟满 | 后果/失败前进 |
| 某 Actor 连续 2 次没被选中 | 优先给他 spotlight |
| 对话重复/无新信息 | GM 给线索/事件 |

## 6. 回合管线（详细）

```
1. Director 选择 next_actor
2. 构建该 Actor 的上下文
   - 公开 transcript
   - 该 Actor 的私有知识
   - 角色卡/目标/关系
   - 场景 brief
3. Actor 生成结构化输出
4. 如果 request_check：
   a. GM 决定 skill / difficulty / target
   b. Dice Service 掷骰
   c. GM 根据结果叙述
5. 更新状态
   - 公开 transcript
   - 私有知识（谁听到了什么）
   - NPC 态度/时钟/线索
6. Director 判断：
   - 场景继续？
   - 转场？
   - 给真人？
   - 插入事件？
7. 返回 Flutter（流式/分段）
```

**示例（科比特晚宴）：**

```
GM: 你们按了门铃，科比特先生出来了。
Corbitt: 你们好，有什么事吗？
Director → B_Stella
B: 您好，我是 Stella……想邀请您参加餐会。
B.request_check = true
GM: 需要【话术】检定，普通难度，目标 50。
Dice: 81 → 失败。
GM: 科比特礼貌地拒绝：“我刚结束一次会面，实在疲惫。”
Director → A_Human（B 失败，给真人补位）
A: 不用多长时间……Stella 说您是本地区有名的商业家。
A.request_check = true
GM: 需要【话术】检定，普通难度，目标 50。
Dice: 41 → 成功。
GM: 科比特沉吟片刻：“好吧，我收拾一下就过来。”
State: corbitt_patience -1, clue_unlocked: "科比特刚结束一次会面"
Director: 场景目标达成 → 转场/结算
```

## 7. 数据模型（最小可用）

```python
class Scenario:
    id: str
    title: str
    premise: str
    scenes: list[Scene]
    npcs: list[NPC]
    clues: list[Clue]
    ruleset: str

class Scene:
    id: str
    goal: str
    entry: str
    clocks: dict[str, int]
    exits: list[Exit]

class Actor:
    id: str
    type: Literal["human", "ai_pc", "npc", "gm"]
    name: str
    sheet: CharacterSheet
    goals: list[str]
    secrets: list[str]
    relationships: dict[str, int]
    knowledge: KnowledgeBase

class Event:
    id: str
    session_id: str
    scene_id: str
    actor_id: str
    type: Literal["narration", "dialogue", "action", "check", "roll", "state"]
    content: str
    visible_to: list[str]
    timestamp: datetime

class Roll:
    id: str
    session_id: str
    actor_id: str
    skill: str
    skill_value: int
    difficulty: str
    die: int
    outcome: str
    proof: str | None
    timestamp: datetime
```

**SQLite 表：**

- `scenarios`（或直接 YAML 文件）
- `sessions`
- `actors`
- `events`
- `rolls`
- `memories`（摘要/知识）

## 8. 成本与延迟

### 8.1 成本

- 每个 beat 大约 1 次 Actor 调用 + 0–1 次 GM 调用 + 0–1 次骰子/叙述；
- 4 个 Agent × 30 beat ≈ 120 次调用；
- 用便宜模型（如 DeepSeek/Qwen）做 AI 玩家，强模型做 GM；
- 单次 15–20 分钟 session，成本可控制在 **几毛到几块钱**；
- 个人玩完全可以接受；示例归档零成本。

### 8.2 延迟

- 顺序执行 Agent，避免并发抢话；
- 流式输出，先显示“正在思考/正在说话”；
- 骰子动画 0.8–1.2 秒，给玩家“仪式感”；
- 慢线任务（摘要/知识更新）后台跑，不阻塞下一回合；
- 每个 Agent 限制 1–3 句话，减少生成时间。

### 8.3 预算控制

- 每 session 最大 beat 数（如 60）；
- 每 Agent 最大 token；
- 超出预算提示“本场结束/继续请开新场”；
- 显示 token 消耗（作品加分项）。

## 9. 评估与演示

### 9.1 评估指标

| 指标 | 怎么测 |
|---|---|
| **角色一致性** | 同一角色 10 次输出，是否偏离性格/目标 |
| **信息边界** | 是否出现“B 知道了 C 的秘密” |
| **规则忠实度** | 骰子结果是否被 LLM 篡改 |
| **对话张力** | 是否有冲突/分歧/悬念，而不是互相附和 |
| **玩家 agency** | 真人的行动是否改变结果 |
| **成本/延迟** | 每 beat 的 token/耗时 |
| **可玩性** | 自己玩 5 局，记录“想继续玩”的节点 |

### 9.2 评估脚本

```
scripts/run_session.py
  --scenario dinner_with_mr_hale
  --mock            # 无 API key，固定响应，适合 CI/演示
  --real            # 真实 LLM
  --seed 42
  --out transcripts/
```

输出：

- 完整 transcript（Markdown）；
- 每 beat 的 actor/token/latency；
- 骰子日志；
- 自动检查：
  - 没有角色替别人说话；
  - 没有秘密泄露；
  - 骰子结果与日志一致；
  - 场景目标达成/时钟状态。

### 9.3 演示模式

- **示例归档**：仓库内置一段真实跑团 transcript + 骰子日志，没有 API key 的人也能读；
- **Real 模式**：BYOK，填 API key 真玩；
- **Demo 视频**：3–5 分钟，展示“B 失败 → A 补位 → 成功”的完整流程；
- **GIF**：README 顶部放 10 秒关键回合。

## 11. 版权：科比特先生的风险

**重要：** “科比特先生”（Mr. Corbitt）出自《克苏鲁的呼唤》的经典模组 *The Haunting*，是 Chaosium 的版权内容。把它直接放进公开 GitHub 项目，有侵权风险。

**建议：**

1. **改名 + 原创剧本**：把“科比特先生”换成原创角色（如“顾先生 / Mr. Hale”），保留“社交邀请 + 话术检定 + 失败补位”的结构；
2. **不要使用 CoC 规则文本/角色卡**：用你自己的 d100 技能列表；
3. **如果坚持用 CoC 风格**：在 README 标注“inspired by”，非商业、粉丝作品，并附上版权声明；但这仍有风险，原创最安全；
4. **代码 MIT，剧本 CC-BY-NC 或原创**：分开授权。

**原创替代示例：**

> **《顾先生的晚宴》**  
> 1930 年代，上海。你们受雇调查一位神秘商人“顾先生”，怀疑他与最近的人口失踪有关。你们决定以“邻居”的身份，邀请他参加一场小型晚宴，套取信息。  
> 场景目标：让顾先生接受邀请。  
> 耐心时钟：3。  
> 线索：他刚结束一次“会面”；他的袖口有泥；他不吃荤。

这样既有氛围，又避免版权问题。

## 13. 风险与对策

| 风险 | 对策 |
|---|---|
| AI 互相客套/冷场 | Director + 目标/秘密/冲突 + 插入事件 |
| AI 抢话/替别人说话 | 输出 schema + 禁止规则 + 单 beat 限制 |
| 信息泄露 | KnowledgeBase + visible_to + 测试 |
| LLM 篡改骰子 | 骰子服务端权威 + GM 先声明后掷 + 日志校验 |
| 成本/延迟 | 便宜模型 + 1–3 句话 + 预算上限 + 后台慢线 |
| 版权 | 原创角色/剧本 + 自研 d100 + 分开授权 |
| 范围膨胀 | 先做 1 场景 1 真人 2 AI，再做 3–6 人 |
| “不好玩” | 自己玩 5 局，记录“想继续”的节点；优先做冲突/代价/角色目标 |

## 14. 结论

**做，而且这个方向比“AI 写小说”更适合你。**

- **它是个好作品**：多 Agent、状态机、规则引擎、骰子、Flutter、评估，都能讲；
- **它是个好玩具**：你自己会玩，AI 队友的意外行为就是乐趣；
- **它的核心不是 LLM，是编排**：Director + 信息边界 + 骰子权威；
- **首版要小**：1 个原创场景 + 1 真人 + 2 AI 玩家 + 1 GM + 1 NPC + d100 + 文本；
- **版权要干净**：不要直接用品社的“科比特先生”，做原创致敬。

**一句话：**

> **“一个真人，混在一群 AI 玩家里跑团；你负责意外，AI 负责演戏，骰子负责公平。”**
